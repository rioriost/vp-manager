# 判断JSONは原文に対応する全件を渡す

この文書は、`analyze`が作ったジョブに読み補正を適用する利用者とホストAI向けです。まず例と「既存の判断を残して更新する」を読み、フィールドの細部は表で確認してください。JSONはデータとして検査され、コードやコマンドとして実行されません。

`apply-decisions`へ渡すJSONは、そのジョブで使う判断一式です。前回との差分だけを渡すと、渡さなかった補正や候補の受入れは保持されません。`job.json`に保存された既存の`decisions`を読み、必要な判断を残したうえで変更してください。

## 原文の位置と読みを対応させる

原文が`C++を紹介します。`で、対象の`units[].id`が`u0001`だった場合の例です。`source_revision`は例の文字列を使わず、対象ジョブの`job.json`から実際の値を転記します。区間の位置は元の`source_text`に対するUnicodeコードポイント数で、0から数え、`end`の文字を含みません。

```json
{
  "schema_version": 1,
  "source_revision": "対象job.jsonのsource_revisionをそのまま転記",
  "overrides": [
    {
      "unit_id": "u0001",
      "start": 0,
      "end": 3,
      "expected": "C++",
      "reading": "シープラスプラス"
    }
  ],
  "dictionary_entries": [],
  "accept_candidates": []
}
```

この例では、原文の3コードポイントを読み上げ用のかな表記へ置換します。原文と元のPPTXは変更しません。読みの長さが変わっても、後続の補正位置は同じ元原文を基準に記述します。

```sh
uv --directory /absolute/vp-manager run vp-manager apply-decisions /absolute/job --file /absolute/job/decisions.json --json
```

`source_revision`が古い、`expected`が指定位置の原文と一致しない、範囲が重なる場合は拒否されます。結合文字や絵文字の連結など、Unicodeの文字列を途中で分断する位置も使えません。

## フィールドは決められた名前と型で記述する

| トップレベルの項目 | 型 | 内容 |
|---|---|---|
| `schema_version` | 整数 | 必須。現在は`1` |
| `source_revision` | 文字列 | 必須。対象`job.json`の同名の値と完全一致 |
| `overrides` | 配列 | 原文に対応する読み補正。省略時は空配列 |
| `dictionary_entries` | 配列 | 一時辞書へ追加する新規語。省略時は空配列 |
| `accept_candidates` | 文字列の配列 | 表記を保つと判断した候補のID。省略時は空配列 |

トップレベルに独自項目を追加すると拒否されます。判断理由や比較音声の説明は、JSONへ混ぜず、利用者への説明や制作メモとして残します。

`overrides`の各要素には、次の5項目をすべて指定します。追加項目は使えません。

| 項目 | 型 | 内容 |
|---|---|---|
| `unit_id` | 文字列 | `job.json`の`units`にあるID |
| `start` | 整数 | `source_text`内の開始位置。0以上 |
| `end` | 整数 | 終了位置。`start`より大きく、原文長以下 |
| `expected` | 文字列 | 元原文の`source_text[start:end]`と完全一致する文字列 |
| `reading` | 文字列 | ひらがな・カタカナと通常の句読点などによる読み。かなを1文字以上含む |

読みに英字、数字、SSML、制御文字は含められません。数値や単位をかなにする場合も意味を維持します。例えば符号やパーセントを省かず、元の発言をどう読むかを指定します。意味を変える書き換えには別の依頼が必要です。

## 候補を解決する方法を選ぶ

候補を解決済みにする方法は、候補の範囲全体を覆う`override`を渡すか、その候補IDを`accept_candidates`へ入れることです。候補IDは`job.json`の`candidates[].id`を使い、重複を避けます。

記号を含む候補は全体の読み置換が必要です。例えば`C++`を`C`だけ置換しても解決しません。`accept_candidates`で記号付き語をそのまま通すこともできません。これは、記号付きの登録語でエンジンの異常終了を観測したための入力制約です。

辞書への追加だけでは、対応する候補は解決済みになりません。記号のない候補に辞書を効かせて元の表記で合成するなら、対象IDを`accept_candidates`にも指定します。辞書にある語でも、文脈で読みが変わる場合は、その出現位置に対する読み補正を使います。

`accept_candidates`は、読み方の検討を済ませて原表記を使う判断です。音声の発音や自然さを聴いて受け入れた記録とは別です。聴取前の音声を品質合格にする効果はありません。

## 辞書へ渡すのは新規語だけ

`dictionary_entries`の各要素はVOICEPEAKの既知の形式に限定します。次はフィールドの形を示す例です。実際には既存辞書と衝突しない表記と、対象語の正しい読みを選びます。

```json
{
  "sur": "架空語",
  "pron": "サクラモチ",
  "pos": "Japanese_Koyuumeishi_ippan",
  "priority": 5,
  "accentType": 0,
  "lang": "ja"
}
```

| 項目 | 型・範囲 | 既定値 |
|---|---|---|
| `sur` | 空白だけでない、1〜140コードポイントの表記 | 必須 |
| `pron` | 1〜140コードポイントのカタカナ読み。長音符は使用可 | 必須 |
| `pos` | `Japanese_Futsuu_meishi`または`Japanese_Koyuumeishi_ippan` | 必須 |
| `priority` | 0〜10の整数 | `5` |
| `accentType` | 0〜読みのモーラ数までの整数 | `0` |
| `lang` | `ja` | `ja` |

`pron`の先頭に小書きの母音・拗音や長音符は使えません。モーラは、例えば`キャット`では3として扱います。数値上有効なアクセントが自然な発音になるとは限らないため、候補音声を聴いて確かめます。

既存の`sur`は上書きしません。同じ判断JSON内の重複も拒否されます。既存語と衝突したときは、原稿内の読み補正に切り替えるか、辞書への追加を取り下げてから再適用します。

合成バッチ中は新規語を一時追加し、終了後に`dic.json`・`user.dic`・`user.csv`を復元します。新規語が使われた全区間を聴取して受け入れた後、`promote-dictionary JOB`で共通辞書へ確定保存できます。未使用語、古い承認、生成時から変わった元辞書では保存しません。

外部変更が見つかると、バックアップと変更後のファイルを保持して`needs_recovery`で停止します。辞書ファイルを手動で上書きせず、`recover-dictionary`の結果と保存先を確認してください。確定保存の成功経路は一時辞書で試験済みです。実辞書への初回保存には、対象音声の実際の聴取確認が残っています。

## 既存の判断を残して更新する

1. `status JOB --json`と`JOB/job.json`で状態、原稿の版、未解決候補を確認する。
2. 保存されている`decisions`を基に、残す`overrides`、`dictionary_entries`、`accept_candidates`を含む全体を作る。
3. 変更する出現位置の読みだけを直し、元原文の範囲と`expected`を照合する。
4. `apply-decisions`を実行し、返された状態と課題を確認する。
5. `render`後に`verify`し、変更した音声と区間のつなぎ目を確認する。

受入れ済みの音声を変更した場合、前の聴取記録で新しい音声を受け入れ済みにしません。初回を含む4回の区間別生成上限とジョブ予算を守り、改善が見込めないときは未解決理由を報告します。

エラーが解決しない場合は、`status --json`の`issues`と該当候補・補正区間を制作担当者へ示してください。原稿全体や音声を共有する必要があるかは別途判断します。

用語の対応：`unit`は原文の段落単位、`candidate`は読みの検討対象、`override`は特定の出現位置への読み補正、`chunk`はエンジンに渡す140コードポイント以内の区間です。`source_revision`は保存した原稿のハッシュで、判断と原稿の取り違えを防ぎます。
